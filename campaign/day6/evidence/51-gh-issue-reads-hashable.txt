[carljm 2026-08-04T01:49:52Z] Currently we consider the type `Hashable` equivalent to the type `object`, which is technically correct, since `object` specifies a non-None `__hash__`, and thus it should be a Liskov violation to ever create a non-hashable Python object. But obviously this doesn't accommodate very well the reality of the (unsound) way that `Hashable` and hashability are used in real-world Python type annotations.

I think we should not consider `Hashable` equivalent to `object`, and we should actually validate the `__hash__` type of the provided type against `Hashable`.

`Iterator` (in typeshed) is a protocol. The protocol includes no hashability requirement. That means that both hashable and non-hashable iterators are assignable to `Iterator`. It's easy to create a non-hashable iterator:

class UnhashableIterator:

######## PR astral-sh/ruff#27441
[ty] Reject unhashable objects for Hashable protocols
MERGED merged 2026-08-05T18:01:00Z
https://github.com/astral-sh/ruff/pull/27441
## Summary

- Stop treating protocols that explicitly require `__hash__` as equivalent to `object`, because (even though it's not Liskov sound) subclasses disable hashing with `__hash__ = None`.
- Reject unhashable classes, built-in containers, and mutable dataclasses for both standard-library `Hashable` spellings and equivalent user-defined protocols.
- Preserve meaningful `Hashable | T` union members while keeping hashable `object()` sentinel values assignable to hash protocols.
- Adjust pandas and static-frame benchmark diagnostic ceilings for newly surfaced hashability errors.

Closes https://github.com/astral-sh/ty/issues/4157

## Test plan

- Added mdtests covering annotation-only and assigned `ClassVar[None]`, inherited and final unhashable classes, `list`/`dict`/`set`, both `Hashable` imports, equivalent custom protocols, mutable versus frozen dataclasses, valid hashable values, `object()` sentinel defaults, and explicit assignability/subtyping checks.
- Updated existing mdtests for `object` non-equivalence and preservation of unions containing final unhashable classes, mutable dataclasses, type variables, and protocols.


######## PR astral-sh/ruff#29471
[ty] Allow subclasses to restore hashability
MERGED merged 2026-10-19T21:12:34Z

Allow subclasses to disable or restore hashing regardless of an ancestor's hash definition. Validate each `__hash__` against the bound signature of `object.__hash__` or `None`, rejecting incompatible signatures and non-callable values.

Hash definitions do not inherit ancestor type annotations. Final methods and variables still cannot be overridden.

Closes astral-sh/ty#4748.

## Test plan

Manually verified that instance-only hash assignments neither invalidate a valid class hash nor hide an invalid one, that a descriptor can supply a valid hash callable, and that an annotated invalid hash produces one diagnostic.

######## PR astral-sh/ruff#26040
[ty] Model hashability for union simplification
CLOSED merged null
https://github.com/astral-sh/ruff/pull/26040
## Summary

Today, ty effectively treats every type as assignable to `Hashable`, because `object` defines `__hash__`. Normal union simplification would therefore reduce `Hashable | T` to `Hashable` for any `T`. To avoid discarding types that may contain unhashable values, `main` has a narrow exception that preserves `T` when it is a non-final nominal class, since subclasses can disable hashing.

This branch broadens that exception. Finality only tells us whether a class can be subclassed; it does not establish whether its instances are hashable. A final class can explicitly set `__hash__ = None`, implicitly disable hashing by defining `__eq__`, or inherit either behavior from a base class:

```python
from typing import Hashable, final

@final
class Unhashable:
    def __eq__(self, other: object, /) -> bool: ...

def f(value: Hashable | Unhashable) -> None:
    reveal_type(value)  # Hashable | Unhashable
```

This replaces the finality heuristic with a conservative `Always` / `Never` / `Maybe` hashability model. Nominal classes use their effective `__hash__` slot across the MRO, including implicit cancellation and synthesized dataclass members, while TypeVars, TypedDicts, literals, aliases, and structural protocols receive corresponding classifications.

Union normalization now removes the other arm only when every represented value is known to be hashable. The shared pair-preservation hook applies the rule consistently to ordinary and literal union elements, while `object` and exact complements retain their existing universal-union behavior.


######## ISSUE python/mypy#5491
Clean up kludges for handling metaclasses and Type[...] in check_op_reversible
CLOSED created 2018-08-16T20:19:58Z closed 2025-06-09T14:35:54Z
https://github.com/python/mypy/issues/5491
The [current implementation for checking reversible operators][0] contains two kludges that seem to be related to operators, metaclasses, and Type[...]

1. This call to [has_member][1] feels like it ought to be unnecessary/redundant due to the following `analyze_member_access` -- but removing it causes pythoneval's [OpMetaclassAccess](https://github.com/python/mypy/blob/master/test-data/unit/pythoneval.test#L1159) test case to fail.

    (Note: if you remove just that call, you also need to add in a `elif isinstance(member, AnyTyp): return None` after calling `analyze_member_access`)

2. If the reversible operators logic was unable to find a matching operator, it just [tries calling `check_call` on the name directly][2] to get back some generic error message. It seems as if this call ought to always return an error message, but sometimes it surprisingly will not. E.g. see the [TypeTypeComparisonWorks](https://github.com/python/mypy/blob/master/test-data/unit/check-classes.test#L3251) tests in check-classes -- adding an `assert local_errors.is_errors()` causes that test case to crash.

    This feels related to the first TODO in some way -- either we're not handling operators + metaclasses + Type directly, or there are some weird shenanigans happening due to `Any`...

For additional context, see https://github.com/python/mypy/issues/5136 and https://github.com/python/mypy/pull/1806.
