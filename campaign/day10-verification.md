### D10-4 `Never` after `assert f(x) == <int literal>` (ty)

The earlier phase-5 bisect (`campaign/day10/phase5/reduce/`) blamed `assert describe(3) == 4` and the overload order. `repro2/o1.py` to `o8.py` and `q1.py` to `q9.py` show the mechanism:

| Program | ty 0.0.97 / 0.0.99 | mypy | pyright |
|---|---|---|---|
| `o2`: `def g(x: object) -> str`, `assert g(3) == 4`, then `reveal_type(g("a"))`, `reveal_type(g)`, `reveal_type(g(3))` | `Never` three times | `str`, `def (x: object) -> str`, `str` | normal |
| `q3`: `== True`, `== None`, `== b"s"`, `== 4_000`, `4 == g(3)` | `Never` for `g` | normal | normal |
| `q3`: `== 4.5`, `== "s"`, `!= 4` | normal | normal | normal |
| `q5`: `def g(x: int) -> int`, `assert g(3) == 4` | normal | normal | normal |
| `q1`: `if g(3) == 4:` then the branch / the else / after an early `return` | `Never` only in the branch | normal | normal |
| `q4`: `assert k.m(3) == 4` then `k.m`, `k.m(1)`, `k` | `Never` for all three | normal | normal |
| `q7`: `assert g(y) == 4` then `y`, `g` | `Never` for both | normal | normal |
| `r4`: `x = name(n) == 4`; `reveal_type(x)` | `Literal[False]` | `bool` | `bool` |
| `r1`: `assert name(n) == 4` then `n.no_such_attribute`, `name(n, 1, 2)`, `name("not an int")` | `All checks passed!` | 3 errors | 3 errors |
| `o7`: same assert in a function, then `reveal_type(1)` | `Literal[1]` | `Literal[1]?` | |

So the comparison of a `str` with an `int` literal is `Literal[False]`, the code after the assert (or inside the `if`) is unreachable, names looked up there are `Never`, and diagnostics are off there; a literal such as `1` does not depend on a name and prints normally. This follows the ty decisions in ty#3419 (equality narrowing ignores a subclass that overrides `__eq__`, closed completed 2026-07-22) and the generalised equality inference named in ty#4039. Related open reports: ty#4051 (reachability and narrowing of `==` for `str` are inconsistent; its example reveals `Never`), ty#3162 (names in unreachable code leak as `Never`). The false negatives of `r1` are the cost of that design, so no draft: confidence below 0.2 that it would be taken as a bug, and the statement `assert str_value == 4` is itself a mistake.
